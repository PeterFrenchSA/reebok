# Reebok House Manager: Application Review

Reviewed 20 September 2026. Source: `codex/sol-5-6-review`, commit `9a5c424`.
The findings below describe the reviewed baseline, not the current implementation
status. The initial review made no application changes; see the implementation
follow-up at the end for subsequent work and remaining limitations.

## Findings

P1 means address before expanding production exposure or enabling bot bookings.
P2 means a material correctness, operational, or usability issue. Runtime evidence
below comes from synthetic data in an isolated local production-mode instance,
not from the Ubuntu production server.

### P1: Public feedback can expose booking-management credentials

The public feedback response includes booking references and author email
addresses. Anonymous booking management accepts a matching reference and email
without proving access to that email address. In combination, a public feedback
entry enabled an unauthenticated read and edit of its associated booking, both
returning HTTP 200. This is not merely information the UI happens to hide.

Use a public feedback field allowlist. Keep the reference/email entry form, but
have it send a short-lived management link rather than directly authorize access.
Preserve authenticated ownership/admin checks and timing-safe token verification.

Sources: [public feedback](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/feedback/route.ts:31), [anonymous access](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/manage/route.ts:72).

### P1: Reservations can double-book

Availability is checked before creation, outside a transaction that protects the
check and write. Two simultaneous identical requests both returned HTTP 200.
Separately, approving a rejected booking over an existing reservation succeeded:
the approval endpoint does not restrict eligible states or recheck conflicts.
Booking imports also bypass the normal conflict and audit logic (static finding).

Centralize create/edit/approve/import validation. Protect overlap checks and writes
with a database concurrency strategy, including retries where appropriate. A
transaction at the default isolation level alone is insufficient.

Sources: [creation](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/route.ts:296), [approval](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/[id]/approve/route.ts:50), [import](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/finance/import/route.ts:108).

### P1: Room allocation and member booking rules are not implemented end to end

The model supports rooms, but the overlap query treats every booking as occupying
the entire house. A second member booking for a different room returned HTTP 409.
A room-specific booking without any allocation was accepted. An allocation of 20
people to a room with capacity 4 was also accepted.

The shared booking form always submits `EXTERNAL_PUBLIC`, so signed-in members
using that form do not get the intended internal room-selection/pricing workflow.
Validate room existence, bookable state, capacity, duplicates, and occupant totals;
provide a member-aware booking form and room-aware availability.

Sources: [booking form](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/components/BookingRequestPage.tsx:77), [booking validation](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/route.ts:285).

### P1: Pricing can be zero or become incorrect after editing

The guest list and pricing breakdown are independent inputs. A public booking with
one named adult and no breakdown was accepted with total amount zero under the
seed configuration. A note-only edit to an adult-and-child booking changed its
total from 1200 to 1600 because all occupants were repriced as adults. Extending an
internal booking from two nights to four left its total at 200.

Use one validated occupant breakdown, persist it, and use the same pricing service
for quotation, creation, and editing. Decide separately whether an already-approved
booking retains its original tariff version when changed.

Sources: [guest counts and pricing](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/route.ts:280), [edit pricing](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/manage/route.ts:190).

### P1: Starter administrator credentials remain a production feature

The production login page displays sample administrator/member passwords and
prefills a sample account. The seed creates these accounts, and deployment scripts
run the seed by default. If the starter passwords have not been changed, this
provides public privileged access. The actual production passwords were not tested.

Remove production credential display and sample-account creation. Separate safe
reference-data initialization from explicit local demo seeding; use a one-time
administrator bootstrap. Preserve passwords already changed by the operator.

Sources: [login](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/login/page.tsx:98), [seed](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/prisma/seed.ts:108), [deployment seed](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/scripts/update-ubuntu.sh:287).

### P1: A submitting member can see director-only decision details

Members can retrieve their own proposals even after those proposals become
admin-only polls. The response includes private review notes and vote totals.
This was reproduced; casting a member vote in that poll was correctly denied.
Return proposal status to its submitter, but restrict director discussion and
tracking to the selected audience.

Source: [decision visibility and response](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/decisions/route.ts:32).

### P1: Dependencies need a new security update

A fresh audit of the committed lockfile reported 13 affected package entries:
1 critical, 9 high, and 3 moderate. This includes runtime and development/transitive
dependencies; it does not mean 13 vulnerabilities were demonstrated in this app.
Next.js and Nodemailer are among the affected direct dependencies. One Next.js
critical advisory is Windows-specific and does not apply to the Ubuntu host;
image-processing and other advisory exposure still needs targeted assessment.

Update compatible direct dependencies and assess transitive fixes, then rerun the
build and regression tests. Do not blindly run a forced audit fix: the audit's
suggestions include Prisma/ExcelJS downgrades. The existing low-severity-only audit
notes in project documentation no longer describe the current advisory snapshot.

Evidence: `npm audit --json`, run against a fresh install of the committed lockfile.

### P2: Feedback moderation and internal visibility are bypassable

Public feedback defaults to published and accepts the caller's publication flag.
An anonymous request with `visibility=INTERNAL` can retrieve an internal entry if
it has been marked published. Both behaviours were reproduced. Enforce audience
restrictions independently of the requested filter, and make new public feedback
pending moderation unless an explicit trusted workflow publishes it.

Source: [feedback filtering and creation](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/feedback/route.ts:33).

### P2: Maintenance owners can override completed work

A member who submitted a task could reopen it after completion, replace the actual
cost, and assign it to a guest account. Define field-level permissions and allowed
status transitions. Keep completion, actual cost, and assignment under the relevant
admin permission, and add an audit trail for approvals and completion changes.

Source: [task updates](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/maintenance/tasks/route.ts:124).

### P2: Payment and subscription records can become inconsistent

An unauthenticated request could attach a pending payment to another person's
booking. A subscription-payment request with an invalid user returned HTTP 500 but
left a payment row behind. One month of coverage starting 31 January 2027 produced
a next-due date of 3 March. Recording an older coverage period can also move the
due date backwards (static finding).

Require booking ownership or a valid guest management token for payment submission.
Validate references first and write related payment/subscription changes atomically.
Use explicit calendar-month rules. Arrears currently remain manually maintained
even after payment; whether to calculate them automatically is a business decision.

Sources: [payments](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/payments/route.ts:97), [month arithmetic](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/lib/fees.ts:136).

### P2: Import/export needs explicit schemas and safer handling

The booking CSV contains `manageToken` values. Newly generated values are hashes,
not usable raw links, but legacy plaintext values remain possible during rollout
and neither belongs in a finance export. Exports need explicit column allowlists.
CSV formula escaping is absent. Imports can partially succeed, are not deduplicated,
and payment imports omit booking/payer relationships. Add input/row limits, preview,
per-row validation, safe cell escaping, and a clear atomic or resumable import policy.

Sources: [export](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/finance/export/route.ts:55), [CSV serialization](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/lib/csv.ts:4), [import](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/finance/import/route.ts:59).

### P2: The last super-admin can remove their own privileges

Self-deactivation is blocked, but self-demotion is allowed. The sole super-admin
was successfully changed to a guest, leaving zero active super-admins. Protect the
last active super-admin against demotion/deactivation, including concurrent changes.

Source: [user updates](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/users/route.ts:99).

### P2: Deployment and email failures can lose user-visible work

Static inspection found that the updater routes live traffic to a staged release
without sharing its upload directory with the primary release. Existing uploads
are unavailable there, and uploads written during that interval are not copied
back. Use persistent shared upload storage across releases.

Booking/invitation workflows write data before sending mail. A subsequent mail
failure can report failure after the operation succeeded; missing SMTP silently
skips delivery. Booking-link rotation can also invalidate the previous link before
its replacement is delivered. Use a durable notification outbox with retry and
delivery status. No real email delivery or production deployment was attempted.

Sources: [staged deployment](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/scripts/update-ubuntu.sh:256), [approval notification](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/[id]/approve/route.ts:76), [mail transport](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/lib/mail.ts:27).

## Application Purpose And Coverage

The app is a shared-house operations system, not just a public booking website.
It should provide one authoritative reservation calendar, controlled guest/member
self-service, director approvals and governance, and traceable property finances
and maintenance.

| Area | Present today | Important gap |
| --- | --- | --- |
| Public/guest accommodation | Request, pets notice, manage booking, feedback, information board | Secure guest management and moderated feedback |
| Member accommodation | Shared summaries and access to booking pages | Member pricing and usable room selection |
| Admin bookings | Approve/reject/comment, history and audit records | Concurrency, state transitions, shared UI refresh |
| Assets/maintenance | Asset documents and task approval/completion controls | Server-enforced lifecycle and audit history |
| Finances | Member subscription tracking, payments, expenses, CSV/XLSX | Reconciliation rules and reliable imports |
| Decisions | Submission, review, audience selection, voting and tracking | Director privacy, formal quorum/outcome rules |
| Accounts | Role portals, invitations, approval, user management | Demo credentials, super-admin safeguard, role clarification |
| Email | Editable booking templates and notification calls | Delivery tracking; invitations/reminders are not all templated |
| Channel integrations | Connection/settings scaffold | No implemented external reservation synchronization |
| Payments/OCR integrations | Models and API scaffolding | Not verified live gateway or end-to-end OCR capabilities |
| Bot access | Public calendar-data endpoint | No linked identities or scoped, room-aware bot API |

## Confirmed Product Decisions

1. Only registered members and administrators may use the bot for availability.
2. Pending requests hold the relevant dates until an administrator approves or
   rejects them; do not introduce automatic expiry without another decision.
3. Members may reserve rooms or the whole house. Different rooms may be occupied
   concurrently. Guests reserve the whole house only.
4. Administrative authority belongs only to appointed administrators. Shareholding
   alone must not grant approval, editing, moderation, or user-management authority.
   Shareholders have full read-only financial visibility, including itemized
   expenses, payments, individual member fee balances, and financial reports.
   Visibility does not grant editing, payment confirmation, or import authority.
   Director-only discussion and account credentials remain restricted. This
   supersedes the current role-map intent in AGENTS.md, but no runtime permission
   changes have been made yet.
5. There is no existing bot. Telegram is the chosen first integration; WhatsApp
   may be added later if needed. This supersedes the earlier WhatsApp-first
   preference following assessment of its group restrictions.
6. Both private conversations and approved groups are required. This is a product
   requirement, not confirmation that the proposed WhatsApp account is eligible
   for official group API access.
7. The family currently uses a Telegram group. A new WhatsApp group is planned for
   approximately 50-60 family members as part of a future move from Telegram.
   This exceeds the currently documented official WhatsApp group API capacity.

A pending room reservation should block that room and whole-house reservations,
not unrelated rooms. A pending or approved whole-house reservation blocks all
rooms. Rejected/cancelled reservations do not consume availability. Checkout remains
exclusive, permitting same-day turnover unless a cleaning buffer is later requested.

## Bot API Assessment

The current calendar endpoint is not a reliable member-only bot contract. It is
public, ignores requested date parameters, returns only the next 18 months, caps
the result at 2,000 bookings, and omits room allocation. A query for known reserved
dates beyond that horizon returned unrelated bookings but omitted that reservation.
The website can also navigate beyond this feed's horizon, making an empty calendar
misleading even though booking creation may subsequently reject the dates.

Source: [availability endpoint](/Users/peterfrench/Documents/Codex%20Projects/Reebok/reebok-house-manager/src/app/api/bookings/availability/route.ts:5).

### Recommended Contract, Not Yet Implemented

Keep platform adapters thin and use one availability service for the website,
booking validation, and bot. A separate bot service could use a versioned endpoint
such as `GET /api/v1/availability` with explicit check-in, check-out, scope, and room
identifiers. An in-app webhook adapter can call the same service directly.

- Accept bounded date-only ranges in `Africa/Johannesburg`; reject unsupported
  dates rather than return a falsely empty result.
- Return whole-stay and per-room availability, capacity, and pending/confirmed
  occupancy indicators without guest names, email addresses, booking references,
  management links, or private notes.
- Authenticate the integration separately from the human user. A server credential
  alone must not let an unregistered chat participant query the system.
- Link provider user identity to an active member/admin through a short-lived,
  single-use pairing flow initiated from the signed-in portal. Recheck role and
  active status on each request; allow unlinking and credential revocation.
- Use narrowly scoped, revocable credentials for an external bot. Do not pass
  administrator browser cookies or development impersonation headers to it.
- Validate provider webhooks, deduplicate deliveries, bound inputs, and rate-limit
  both the integration and linked user. Never trust a claimed email/display name.
- For later booking support, require explicit user confirmation, use member pricing,
  persist an idempotency key, and atomically recheck/reserve availability. Requests
  remain pending administrator approval and retain a bot-origin audit record.
- Do not claim visibility into Airbnb/Booking.com reservations until synchronization
  or a reliable manual import workflow is actually implemented.

Telegram supports a webhook secret header and update identifiers suitable for
request verification and deduplication. See the [official Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).
WhatsApp also uses a webhook integration; provider/account setup should be chosen
before implementation. See [Meta's WhatsApp webhook collection](https://www.postman.com/meta/whatsapp-business-platform/folder/lboq68h/webhooks).

### WhatsApp Feasibility Follow-Up

Direct integration needs a Meta business portfolio, a WhatsApp Business Account,
and a business phone number. A dedicated house number is recommended rather than
moving an individual's existing number. Our application will need a public HTTPS
webhook, securely stored credentials, verified account linking, and an operational
contact for failures. See [Meta's Cloud API setup documentation](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api).

Meta currently describes ordinary service replies within the 24-hour window opened
by a user's message as free. Outside that window, outbound messages require
approved templates, so a later booking-approval notification is not equivalent to
an arbitrary email template. Chargeable rates depend on recipient market and
message category; confirm rates at launch, including any chosen provider's fees.
See [Meta pricing](https://whatsappbusiness.com/products/platform-pricing/) and
[messaging policy](https://whatsappbusiness.com/policy/).

Official group support exists but should not be assumed available to this project.
Provider documentation lists Official Business Account eligibility and a maximum
of eight participants, with invite-based API-created groups. A fresh direct read of
360dialog's page lists OBA eligibility without the high messaging-limit prerequisite
that appeared in an earlier search extract; do not treat that older extract as a
current requirement. Meta's group documentation could not be retrieved during this
follow-up, so intended-account eligibility still needs confirmation. Regardless,
the documented eight-participant limit does not fit the proposed 50-60-person group,
even if it is newly created. Sources: [360dialog group documentation](https://docs.360dialog.com/docs/messaging/groups)
and [tyntec's own group API reference](https://api.tyntec.com/reference/conversations/v3.html).

Current decision: build the platform-independent availability/access-control core
and Telegram integration first. If WhatsApp is added later, a pinned link in the
family group can lead to private bot chat or the authenticated booking page, but
this is not fulfillment of in-group interaction. The existing Telegram group can
use the same backend for its approved in-group requests;
Telegram documents group commands and private-chat bot interaction in its
[official bot FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).
Do not commit to a 50-60-person WhatsApp group bot under the current documented
limits, or base production on unofficial WhatsApp Web session automation.

When group support is feasible, require both an administrator-approved group and
a linked, active, authorized sender. A shared reply is visible to other participants:
restrict groups receiving member-only data to verified members/admins, and suppress
shared responses when recipient eligibility cannot be established. Never put
personal booking details, financial data, or management tokens into group replies.
Perform later booking confirmation and personal-detail collection privately.

### Telegram Without An AI Model

Recommendation in response to the user's model/cost question: use no AI model for
the first release. A robust API plus a deterministic conversation flow can handle
account linking, accommodation selection, date selection, and availability replies.
Telegram supports commands, keyboards, and callback buttons; those features do not
require a language model. See [Telegram bot features](https://core.telegram.org/bots/features#keyboards).

- Offer a guided Check Availability flow: whole house or rooms, check-in, check-out,
  then a response rendered from the authoritative availability service.
- Accept explicitly formatted date commands as a shortcut. Normalize all inputs
  to property-local dates, and clarify ambiguous text rather than guess.
- Keep durable conversation state scoped to the linked user and chat; another
  group participant must not take over a user's selection or booking confirmation.
- Reauthorize every command and callback. Group approval or command visibility
  alone does not prove the sender's active membership.
- Keep personal booking lookup and later booking details/confirmation private.
  Stage one remains availability-only; later booking requests retain admin approval.
- Return clear pending versus confirmed occupancy without revealing other guests'
  private data. Bound lookups, rate-limit requests, and deduplicate webhook updates.
- There are no model/token charges for this design; hosting, implementation, and
  operational maintenance still have costs.

If unrestricted conversational phrasing becomes important later, an optional
language model can translate a message into a small validated intent/date schema.
It must not determine availability, fees, permissions, or approval. The backend
remains authoritative, unclear inputs require clarification, and mutations require
explicit confirmation. Keep the button flow as a fallback, cap model usage, and
select a model only after testing representative messages. No AI provider/model
has been selected or integrated.

## Focused Visual Improvements

Keep the existing visual language; the main opportunity is task clarity rather
than a redesign.

- Collapse admin navigation on small screens. At a 390-by-844 viewport, the header
  and navigation push main admin content down to roughly 717 pixels.
- Give the booking calendar more width. On the desktop two-column layout, date
  buttons were approximately 24 pixels wide despite considerable unused page space.
- Put pending approvals first, move booking policy settings into a secondary
  section, and distinguish current stays from future confirmed bookings.
- Refresh active, pending, and history panels together after a booking changes;
  their independent state currently allows inconsistent views.
- Add proper labels to remaining controls in user, asset, and maintenance screens.
- Avoid stretched summary cards and repeated section headings. Retain expandable
  booking history and clear pending/confirmed visual states.

- Lint passed in the workspace.

  directory. A clean copy of the committed source with a fresh lockfile install
  passed the production build. The original dependency directory was not altered.
- An isolated PostgreSQL container and production-mode local server were used with
  synthetic accounts and SMTP disabled. No production data or external messages
  were used.
- Successful HTTP checks covered authentication, basic role denial, production
  impersonation-header rejection, cron authentication, normal booking creation and
  approval, sequential overlap rejection, same-day turnover, invitation acceptance
  and approval, member voting and closure, expense CSV import, XLSX export, and
  email-template retrieval.
- Adversarial HTTP/database checks reproduced the runtime findings described above,
  including room allocation/capacity, pricing, and concurrent booking failures.
- Browser checks covered login, the admin modules, guest/member portals, desktop
  booking layout, and mobile navigation. These are smoke checks, not exhaustive
  accessibility or cross-browser certification.
- Live SMTP delivery, payment gateways, external reservation channels, Telegram,

- There is no committed automated critical-workflow test suite. Preserve the

## Remaining Decisions

The original questions and the finance/group-size follow-ups have been answered
in Confirmed Product Decisions. Proposed interpretation: shareholder read-only
access applies to management records, while normal own-booking, proposal,
maintenance-request, and eligible-voting actions remain available.

Implementation must separate financial viewing/export from editing/import rather
than reuse today's combined import/export permission. Financial exports must still
exclude security tokens and unrelated private data. Shareholder financial access
does not authorize publishing those records to the wider family group.

Telegram is now selected for the first integration. A model-free guided flow is
recommended; WhatsApp and optional natural-language AI remain later additions.

Decisions to settle during the relevant implementation phase:

- Retain a tariff snapshot or apply current rates when a booking changes? Should
  stays crossing seasons be priced per night rather than by arrival season?
- Are member arrears maintained manually or calculated from monthly charges and
  confirmed payments? Are billing months calendar-based or anniversary-based?
- What constitutes a passed vote: majority, quorum, tie rule, and whether the
  eligible voter list is fixed at launch?
- Should financial proofs/invoices require authenticated downloads? Uploads are
  public by the current design and must not be described as private storage.
- Is there a booking horizon, minimum notice period, maximum occupancy, or cleaning
  buffer beyond the validated room capacities?

## Suggested Implementation Sequence

1. Fix public-data exposure, guest management access, production seed handling,
   director privacy, dependency advisories, and privileged update boundaries.
2. Implement shared room-aware availability, atomic reservation transitions, and
   consistent member/guest pricing; add regression tests alongside each fix.
3. Add the authenticated read-only bot contract and account pairing, then test
   anonymous/guest/deactivated access, room overlaps, horizons, and webhook replay.
4. Improve navigation and booking-task clarity; reconcile finance and maintenance
   workflow rules and address upload/deployment and email reliability.
5. Enable bot booking only after idempotency, confirmation, concurrency, pricing,
   and approval-notification tests pass.

## Implementation Follow-Up: Telegram Availability

Implemented on the review branch after the user approved the model-free Telegram
approach. No real bot was configured and no production database was modified.

- Added reusable room-aware availability, strict South African date handling,
  explicit 90-night/548-day operating limits and a member-authenticated API.
- Serialized booking creation, editing, approval, rejection and active booking
  imports through a shared database advisory lock. Pending bookings block dates;
  different rooms may overlap. Legacy room bookings without allocations fail closed.

  Changed stays use the current fee configuration. Legacy bookings without counts
  and guest-count changes requiring a new breakdown need administrator assistance

  actions and get itemized, read-only financial records and exports.

  made public submissions pending moderation, restricted director-only decisions,
  and removed management tokens/payment gateway payloads from relevant exports.
- Hid production sample credentials and disabled production demo-account seeding.
  Added explicit first-admin bootstrap for fresh installations without overwriting
  existing accounts. Existing sample accounts still need password changes.
- Added hashed single-use Telegram pairing, private room/date menus, approved-group
  private-chat handoff, revocation checks, authenticated bounded webhooks, persisted
  update deduplication and retryable outbound responses. No AI model is used.
- Added member/admin connection screens, group controls, setup documentation and
  the explicit webhook-registration script. Telegram still cannot create bookings.
